# 智能客服 Agent 企业级能力差距与封板计划

## 1. 文档目的

本文档用于梳理当前智能客服 Agent 与成熟企业级智能客服之间的能力差距，并给出优先级、最小实施方向和验收标准。

本文档不是要求一次性堆叠全部组件。所有改造都应优先复用现有 LangGraph、Agent Runtime、Tool、RAG、Product Service、Session 和 Evaluation 能力，避免无效抽象与框架级重构。

## 2. 当前完成度判断

当前系统已经超过简单 Demo 阶段，核心能力完成度约为 **60%～65%**。

现有能力包括：

- LangGraph Agent 工作流和 Runtime。
- 客服 Hybrid Planner。
- 商品查询、推荐、对比 Tool。
- 商品推荐数量控制，单次最多推荐 5 个。
- 最近推荐列表、商品顺序及当前焦点商品。
- “它、这个、第二个、最后一个”等商品指代解析。
- 完整会话历史保存和回传。
- 商品主说明书限定 RAG 链路。
- Knowledge Base 权限范围控制。
- 订单、物流、售后和模拟转人工 Tool。
- 售后草稿、确认门禁和幂等保护。
- Agent Trace、Runtime/API 测试及 Evaluation 基础能力。
- 最小可用商品管理和客服聊天前端。

## 3. 目标架构

成熟客服的核心回答链路应为：

```text
用户输入
→ 结构化意图识别
→ 商品/订单等实体解析
→ 会话业务状态解析
→ 权威数据源路由
→ 一个或多个 Tool 执行
→ 证据校验
→ LLM 基于证据生成回答
→ 安全检查
→ 状态持久化与链路追踪
```

各模块职责必须清晰：

| 模块 | 主要职责 |
|---|---|
| LLM | 理解自然语言、抽取结构化意图、生成自然回答 |
| 结构化会话状态 | 保存当前商品、推荐顺序、用户约束和待确认操作 |
| Policy Router | 将意图映射到允许的数据源和 Tool 链路 |
| Product Tool | 查询价格、库存、品牌、销售状态等结构化实时事实 |
| 商品主说明书 RAG | 查询连接方式、蓝牙、兼容性、充电、按键和故障处理 |
| 政策 RAG | 查询退换货、保修、配送等企业政策 |
| 业务 Tool | 查询订单、物流、创建售后和转人工 |
| Evidence Gate | 无可靠证据时拒绝编造 |
| LangGraph | 编排 Planner、Tool、Reflection、Final 和状态流转 |

## 4. P0：回答准确性的核心链路

### 4.1 结构化意图与实体抽取

#### 当前差距

当前系统同时使用 LLM Planner 和 `_is_recommend`、`_is_manual_question`、`_is_order` 等规则函数，但意图分类粒度不足，不能稳定判断一个商品问题应查询商品数据库还是主说明书。

例如：

```text
“第二个支持蓝牙吗”
```

系统能够识别“第二个”对应的商品，但不一定能稳定识别“支持蓝牙”属于商品说明书事实。

#### 最小实施方向

定义受控的结构化意图结果，不新增独立模型服务：

```json
{
  "intent": "product_document_fact",
  "product_reference": {
    "type": "ordinal",
    "value": 2
  },
  "required_source": "primary_manual",
  "confidence": 0.95
}
```

首批意图至少包括：

- `product_recommendation`
- `product_realtime_fact`
- `product_document_fact`
- `product_comparison`
- `policy_question`
- `order_query`
- `logistics_query`
- `after_sales`
- `human_handoff`
- `clarification`

LLM负责理解开放表达，代码负责校验枚举、字段和允许的数据源。

#### 验收标准

- “多少钱、是否有货”稳定路由至 Product Tool。
- “支持蓝牙吗、怎么连接、兼容 Mac 吗”稳定路由至商品主说明书 RAG。
- “退货期限多久”稳定路由至政策知识库。
- 无法确定商品时先澄清，不跨商品检索。
- 意图结果进入 Trace，能够回放和评测。

### 4.2 权威数据源路由

#### 当前差距

系统已有多个 Tool，但缺少统一的“意图 → 权威数据源”策略层。

#### 最小实施方向

建立固定映射：

| 事实类型 | 权威数据源 |
|---|---|
| 商品价格、库存、销售状态、品牌 | Product Service / Product Tool |
| 商品连接、蓝牙、兼容性、充电、按键、安装、故障 | 商品主说明书 RAG |
| 退换货、保修、配送政策 | 政策知识库 RAG |
| 订单和物流状态 | Order / Logistics Tool |
| 售后创建 | After-sales Tool + pending/confirm 门禁 |

#### 验收标准

- 不使用 RAG 回答实时价格和库存。
- 不使用 LLM 常识回答商品能力和说明书事实。
- 不允许 Planner 绕过知识库、商品和文档 scope。

### 4.3 稳定的多步 Tool 链路

#### 当前差距

商品身份解析、商品查询和说明书 RAG 已分别存在，但串行调用还不稳定。

#### 目标链路

```text
“第二个支持蓝牙吗”
→ 从 last_recommendations 解析第二个 product_code
→ search_products(product_code)
→ 获得 product_id 和 primary_manual_document_id
→ knowledge_search(query, product_id, document_id, allowed_scope)
→ Evidence Gate
→ Final Answer
```

#### 验收标准

- 全链路不依赖商品名称模糊猜测。
- 主说明书缺失时明确返回缺失原因。
- 多 primary 脏数据时拒绝跨文档回答。
- Tool 中途失败时不继续生成确定性商品结论。

### 4.4 统一证据门禁

#### 当前差距

不同回答链路对“无证据”的处理方式不完全统一。

#### 最小实施方向

- 商品实时事实必须有 Product Tool 成功结果。
- 商品说明书事实必须有当前商品主说明书的检索证据。
- 政策问题必须有允许知识库中的政策证据。
- 订单和物流必须有对应业务 Tool 结果。
- 没有证据时使用明确、可区分的拒答原因。

#### 验收标准

- 不将历史回答作为动态事实的唯一依据。
- 不把其他商品说明书内容用于当前商品。
- Trace 中记录证据来源、document_id、product_id 和拒答原因。

## 5. P1：记忆与会话管理

### 5.1 Token 预算与滑动窗口

#### 当前差距

当前客服保存并回传完整对话历史，短期连贯性较好，但会话持续增长后会增加成本，并最终触及模型上下文限制。

#### 第一阶段建议

采用 **5000 Token 消息预算 + 滑动窗口**：

- System Prompt 永久保留。
- 当前用户问题永久保留。
- 本轮 Tool 证据永久保留。
- 结构化客服状态不参与消息滑动删除。
- 从最早的完整对话轮次开始删除。
- user、assistant 和对应 Tool 消息按完整轮次删除。
- 不从单条消息中间截断文本。
- Tool 大结果只保存必要字段和证据摘要。
- Token 阈值必须配置化，不能散落硬编码。

#### 第二阶段建议

在滑动窗口之上增加：

- 早期历史滚动摘要。
- 最近 8～10 轮原始对话。
- 结构化业务状态。
- 按需检索的长期记忆。

#### 验收标准

- 长会话不超过配置的模型输入预算。
- 删除早期消息后，“它、第二个、当前订单、待确认售后”仍能正确解析。
- 不删除安全规则和未完成业务状态。
- Token 裁剪行为进入 Trace。

### 5.2 完善结构化业务状态

现有商品状态应继续保持字段少、职责明确：

```text
focused_product_code
last_recommendations
product_filters
current_order
pending_after_sales
```

后续可以按真实需求补充：

- 用户本次会话预算。
- 使用场景和品牌偏好。
- 当前对比商品集合。
- 当前订单。
- 状态更新时间和过期时间。

#### 状态更新原则

- 用户明确指定商品时切换焦点。
- 新推荐覆盖最近推荐列表，不无限追加为当前候选。
- “第几个”只解析最近一次推荐列表。
- 普通 Tool 查询不能无条件覆盖当前焦点。
- 新会话清空会话级业务状态。

### 5.3 并发与跨实例一致性

#### 当前差距

进程内协调锁不能完整覆盖多 worker、多实例和旧状态覆盖问题。

#### 建议方向

- Session 使用版本号或 CAS 原子更新。
- 售后 reservation 使用可持久化的原子状态。
- 明确 reservation TTL、成功清理和失败恢复策略。
- 同一 conversation 的并发请求需要顺序化或冲突检测。

#### 验收标准

- 同一售后确认只执行一次。
- 失败请求不能用旧 pending 覆盖成功请求的清理结果。
- 跨 worker 行为与单 worker 一致。

## 6. P1：RAG 质量

### 6.1 商品主说明书约束

必须持续保证：

- Product 有效且在允许状态。
- Document 有效、未软删除。
- 文档解析成功。
- 文档类型为 `manual`。
- 绑定关系为 `primary`。
- knowledge base 位于服务端允许范围。
- 多 primary 脏数据拒绝处理。

### 6.2 检索质量评估

不要先假设必须增加 BM25 或 Reranker，应先建立测试集并测量：

- 文档路由准确率。
- Chunk Recall@K。
- 型号精确匹配率。
- 上下文相关性。
- 回答忠实度。
- 无答案识别率。

只有现有向量检索不能达到业务指标时，再引入：

- Dense + BM25/Sparse 混合检索。
- Reranker。
- Query Rewrite。
- Parent/Child Chunk 或标题增强。

## 7. P2：产品体验

### 7.1 客服前端产品化

当前前端可用于功能验证，后续最小产品化能力包括：

- 商品卡片：图片、名称、价格、库存、商品编码。
- 多商品编号与选择按钮。
- “查看详情”和“比较”入口。
- 说明书证据来源。
- 售后确认卡片。
- 转人工状态。
- 用户赞/踩反馈。
- 清晰的新会话和当前会话状态。

### 7.2 真实人工客服协同

当前为模拟转人工。成熟系统需要：

- 转人工队列。
- 坐席分配。
- 对话和业务状态移交。
- 等待、接入、处理中、完成等状态。
- 人工处理结果回流。

该能力不是当前 Agent 核心封板的前置条件，可以独立建设。

## 8. P2：可观测性与运营

建议至少监控：

- 意图识别准确率。
- 商品实体解析成功率。
- Tool 调用成功率。
- 多步链路完成率。
- RAG 有证据率。
- 无证据正确拒答率。
- 回答忠实度。
- 首次解决率。
- 转人工率。
- 平均响应延迟。
- 单轮 Token 和模型成本。

每轮 Trace 至少包含：

```text
conversation_id
turn_id
intent
resolved_entities
selected_source
tool_calls
tool_results
evidence
final_answer
fallback_reason
latency
token_usage
```

## 9. P2：Evaluation 测试体系

### 9.1 核心业务测试集

必须覆盖：

- 单商品推荐后的连续指代。
- 多商品推荐后的第一个、第二个和最后一个。
- 商品焦点切换。
- 价格、库存等实时事实。
- 蓝牙、连接、兼容性等说明书事实。
- 商品无主说明书。
- 主说明书无答案。
- 多 primary 脏数据。
- 商品不存在或下架。
- 允许知识库隔离。
- 无库存和无可售商品。
- 订单、物流和售后确认。
- 提示词注入。
- 重试、并发和重复请求。
- 超长会话的 Token 裁剪。

### 9.2 建议指标

封板前核心用例应满足：

- 路由准确率达到项目约定阈值。
- 商品实体解析关键用例 100% 通过。
- 无证据场景不产生确定性幻觉。
- Tool 权限和 scope 测试 100% 通过。
- 售后确认门禁关键用例 100% 通过。
- 回归测试无 P0/P1 失败。

具体数值应基于固定测试集定义，不使用没有测试口径的“90%+”宣传指标。

## 10. P3：安全、合规与治理

后续企业化需要补充：

- 手机号、身份证、银行卡和地址等 PII 脱敏。
- Tool 参数、Trace、日志和 API 返回统一脱敏。
- 数据保留期限。
- 用户会话删除能力。
- 租户和知识库隔离。
- 操作审计。
- 输出合规和敏感内容检查。
- 模型、Prompt、Tool Schema 和知识文档版本追踪。

## 11. 推荐实施顺序

### 阶段 A：核心准确性

1. 结构化意图分类。
2. 意图到权威数据源路由。
3. 商品查询到主说明书 RAG 的多步链路。
4. 统一证据门禁。
5. 核心 Evaluation 数据集。

完成后，核心能力预计可达到 **75%～80%**。

### 阶段 B：长会话稳定性

1. 5000 Token 配置化预算。
2. 完整轮次滑动窗口。
3. Tool 结果裁剪。
4. 结构化状态保护。
5. 长会话回归测试。

### 阶段 C：生产可靠性

1. Session 原子更新。
2. 跨 worker 售后 reservation。
3. PII 脱敏。
4. 指标、告警和成本监控。

### 阶段 D：产品化

1. 商品卡片和证据来源。
2. 用户反馈。
3. 真实转人工协同。
4. 运营数据闭环。

## 12. 当前最优下一步

当前最值得优先开发的不是新增更多 Tool，而是完成以下闭环：

```text
结构化意图识别
→ 商品实体和会话焦点解析
→ 权威数据源路由
→ 多步 Tool 执行
→ 证据门禁
→ LLM 自然回答
```

第一条验收用例应为：

```text
用户：推荐两个鼠标
客服：返回商品 A、商品 B
用户：第二个支持蓝牙吗
系统：解析商品 B
系统：查询商品 B 的主说明书
客服：依据说明书证据回答；无证据时明确拒答
```

该用例跑通后，再扩展“如何连接、兼容什么系统、怎么充电、按键有什么功能”等同类型问题。
