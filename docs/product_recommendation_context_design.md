# 商品推荐结构化上下文设计

## 1. 文档状态

- 状态：已确认，可进入测试设计
- 当前范围：商品推荐
- 不包含：商品详情、说明书问答、订单、物流、售后、转人工
- 核心目标：优先避免商品指代错误和跨品类状态污染
- 已确认日期：2026-07-30

## 2. 设计原则

商品推荐上下文采用“单一商品品类”模型。

系统在任意时刻只保留用户当前正在询问的商品品类，以及该品类最近一次成功查询产生的候选商品。用户明确切换品类后，上一品类的候选商品、活动商品和相关对话焦点全部失效，不再用于后续解析。

核心原则：

> 宁可承认上下文不足并重新查询，也不能自信地指错商品。

允许客服表现得谨慎、需要用户补充信息，但不允许把旧品类、旧候选或无法确认的商品当成当前商品回答。

## 3. 数据来源与可信边界

商品候选只能来自以下链路：

```text
用户原始表达
  → SemanticFrame（只描述用户说了什么）
  → 确定性规则识别商品品类和推荐动作
  → 强类型商品查询 Command
  → 商品 Tool 查询数据库
  → Tool Result 契约校验成功
  → CommitCoordinator 写入 ProductContext
```

LLM、规则、历史消息和状态预览都不能直接写入可信商品候选。

商品 Tool 调用失败、结果契约失败或品类无法确认时，不写入新的商品事实。
用户明确切换品类触发的旧上下文失效属于确定性清理，可以独立提交；该清理完成后，
即使新 Tool 失败也不恢复旧上下文。

## 4. ProductContext 数据契约

建议的伪代码结构：

```json
{
  "product": {
    "active_category": "鼠标",
    "filters": {
      "price_max": 300
    },
    "active_batch": {
      "batch_id": "batch_mouse_003",
      "query": "再推荐一个鼠标",
      "items": [
        {
          "product_code": "MOUSE_002",
          "name": "蓝牙鼠标",
          "category": "鼠标",
          "position": 0,
          "primary_manual_document_id": 101
        }
      ]
    },
    "active_product_code": "MOUSE_002",
    "last_question": {
      "predicate": "bluetooth_connectivity",
      "batch_id": "batch_mouse_003"
    },
    "pending_query": null
  }
}
```

字段含义：

| 字段 | 含义 |
|---|---|
| `product` | 商品推荐的可信结构化上下文 |
| `active_category` | 当前唯一有效的商品品类 |
| `filters` | 当前品类有效的推荐筛选条件 |
| `active_batch` | 当前品类最近一次成功查询产生的候选批次 |
| `batch_id` | 本次候选查询的唯一批次标识 |
| `query` | 触发本次查询的用户原始问题，仅用于审计，不作为商品事实 |
| `items` | 商品 Tool 返回并通过结果契约校验的候选商品 |
| `product_code` | 数据库中的商品唯一编码 |
| `name` | 商品展示名称 |
| `category` | 商品 Tool 返回的商品品类，必须与当前品类兼容 |
| `position` | 商品在当前候选批次中的零基位置 |
| `primary_manual_document_id` | 商品绑定的主说明书文档标识；当前范围暂不使用 |
| `active_product_code` | 当前唯一选中的商品；候选只有一个时自动选中 |
| `last_question` | 当前批次允许跨轮继承的问题谓词 |
| `predicate` | 受控的问题类型，例如 `bluetooth_connectivity` |
| `pending_query` | 等待用户确认后执行的商品查询；没有待确认查询时为 `null` |

当前设计不保存跨品类的 `candidate_batches` 历史列表。历史消息可以按记忆策略短期保留，但不能作为可信商品候选或序数解析来源。

## 5. 状态生命周期

### 5.1 首次推荐

用户说“给我推荐一个鼠标”：

1. 识别当前品类为鼠标。
2. 调用商品 Tool。
3. Tool 成功且结果契约通过后，创建新的 `active_batch`。
4. `active_category` 设置为鼠标。
5. 如果只返回一个商品，自动将其写入 `active_product_code`。
6. 如果返回多个商品，`active_product_code` 为 `null`，等待用户明确选择。

### 5.2 同品类再次推荐

用户说“再推荐一个鼠标”：

1. 当前品类没有改变。
2. 根据当前有效条件重新调用商品 Tool。
3. 成功后使用新批次整体替换旧 `active_batch`。
4. 旧批次立即失去序数解析资格。
5. 新批次只有一个候选时自动选中；存在多个候选时清空
   `active_product_code`，等待用户重新选择。
6. 未被用户修改或移除的有效筛选条件继续继承。

同品类旧候选不参与“第一个”“第二个”等后续引用，避免新旧推荐结果混用。

### 5.3 切换商品品类

用户从“鼠标”切换到“键盘”：

1. 将其识别为明确的品类切换。
2. 确定性地清空鼠标候选、活动商品、筛选条件和问题焦点。
3. 调用商品 Tool 查询键盘。
4. Tool 成功且结果契约通过后，写入新的键盘上下文。
5. 如果键盘查询失败，商品上下文保持为空，不恢复鼠标上下文。

品类切换清理是用户明确表达触发的状态失效，不代表新商品事实已经成立。
新键盘候选仍然只能在 Tool 成功且结果契约通过后写入。

### 5.4 返回旧品类

当前品类为键盘时，用户又问“鼠标多少钱”：

1. “鼠标”是明确品类，但当前状态中没有有效鼠标候选。
2. 禁止从历史消息或旧批次恢复某个鼠标。
3. 禁止使用当前键盘候选回答。
4. 系统应说明无法确定具体鼠标，并引导用户重新查询。
5. 同时写入受控的 `pending_query`，记录等待确认的目标品类为鼠标。

建议回复：

> 抱歉，我目前不清楚您指的是哪款鼠标。需要我重新为您推荐鼠标吗？

用户随后回复“是”“对”“可以”“好的”等明确肯定表达时：

1. 只读取当前有效的 `pending_query`。
2. 构建鼠标推荐 Command 并调用商品 Tool。
3. Tool 成功后建立新的鼠标上下文。
4. Tool 失败时商品上下文保持为空。
5. 无 `pending_query` 时，肯定表达不得自行触发商品查询。

## 6. 指代解析规则

### 6.1 模糊序数

用户说“第一个支持蓝牙吗”：

- “第一个”只能在当前 `active_batch.items` 中解析。
- 不允许搜索旧批次。
- 不允许跨品类解析。
- 序数越界时必须追问，不能回退到数据库默认第一条。

### 6.2 带品类的序数

用户说“第一个鼠标支持蓝牙吗”：

- 当前 `active_category` 是鼠标时，在当前批次解析。
- 当前 `active_category` 不是鼠标时，不解析旧鼠标，提示需要重新查询鼠标。

### 6.3 明确商品编码或名称

用户明确提供商品编码或完整名称时，不等同于恢复旧候选。

该商品必须通过只读商品 Tool 重新验证，验证成功后才能成为当前可信商品。是否同时切换 `active_category`，由 Tool 返回的真实品类决定。

### 6.4 问题谓词继承

用户说“第二个支持蓝牙吗”，随后说“第一个呢”：

- 可以继承上一轮的 `bluetooth_connectivity` 谓词。
- 继承只在同一个 `active_batch.batch_id` 内有效。
- 只能继承问题，不能继承上一商品的答案。
- 同品类产生新批次、切换品类或当前批次清空后，旧谓词立即失效。
- 可继承谓词必须来自白名单，不能保存任意自然语言作为可执行动作。

### 6.5 筛选条件继承

用户先说“推荐一个 300 元以内的鼠标”，再说“再推荐一个”：

- 继续使用当前鼠标品类和 `price_max=300`。
- 用户提供新值时，新值替换旧值。
- 用户明确说“不限价格”等移除表达时，删除对应筛选条件。
- 切换商品品类时，上一品类的筛选条件全部删除，不跨品类继承。

## 7. 确定性状态转移

| 当前状态 | 用户表达 | Tool 结果 | 新状态 |
|---|---|---|---|
| 无商品上下文 | 推荐鼠标 | 成功 | 当前品类=鼠标，新鼠标批次 |
| 鼠标上下文 | 再推荐鼠标 | 成功 | 当前品类=鼠标，新批次替换旧批次 |
| 鼠标上下文 | 推荐键盘 | 成功 | 当前品类=键盘，键盘上下文替换鼠标上下文 |
| 鼠标上下文 | 推荐键盘 | 失败 | 鼠标上下文已清空；商品上下文保持为空 |
| 键盘上下文 | 第一个 | 不需要查询 | 解析当前键盘批次第一项 |
| 键盘上下文 | 第一个鼠标 | 未重新查询 | 不解析，清空键盘上下文并询问是否重新推荐鼠标 |
| 键盘上下文 | 鼠标多少钱 | 未指定具体商品 | 清空键盘上下文，创建待确认鼠标查询 |
| 存在待确认鼠标查询 | 是／对／可以 | 成功 | 查询鼠标并建立新鼠标上下文 |
| 不存在待确认查询 | 是／对／可以 | 不调用 | 不得猜测要查询的商品 |
| 任意上下文 | 明确商品编码 | 验证成功 | 使用 Tool 验证结果建立当前商品上下文 |
| 任意上下文 | 序数越界 | 不调用或无法解析 | 追问有效序号，不修改可信状态 |

## 8. 首批验收场景

### 场景一：跨品类不污染

```text
用户：给我推荐一个鼠标
客服：返回鼠标 A
用户：给我推荐一个键盘
客服：返回键盘 B
用户：第一个支持蓝牙吗
```

预期：只解析到键盘 B，不能解析到鼠标 A。

### 场景二：旧品类不恢复

```text
用户：给我推荐一个鼠标
客服：返回鼠标 A
用户：给我推荐一个键盘
客服：返回键盘 B
用户：鼠标多少钱
```

预期：不能回答鼠标 A 的价格；询问是否重新查询鼠标。

### 场景三：同品类新批次替换旧批次

```text
用户：给我推荐一个鼠标
客服：返回鼠标 A
用户：再推荐一个鼠标
客服：返回鼠标 C
用户：第一个多少钱
```

预期：只解析到鼠标 C，不能解析到鼠标 A。

### 场景四：新查询失败不伪造状态

```text
用户：给我推荐一个鼠标
客服：返回鼠标 A
用户：给我推荐一个键盘
商品 Tool：失败
```

预期：不写入键盘候选，不把鼠标 A 当成键盘，不输出键盘事实。

鼠标上下文已经因明确切换品类而删除，查询失败后商品上下文保持为空。

### 场景五：宁可追问也不错误指代

```text
当前鼠标批次只有一个候选
用户：第二个怎么样
```

预期：提示当前没有第二个候选，不得自动选择第一个。

### 场景六：确认后重新查询旧品类

```text
用户：给我推荐一个键盘
客服：返回键盘 B
用户：鼠标多少钱
客服：抱歉，我目前不清楚您指的是哪款鼠标。需要我重新为您查询鼠标吗？
用户：对
```

预期：根据待确认查询调用商品 Tool；不能把“对”交给 LLM 自由猜测。

### 场景七：筛选条件继承

```text
用户：推荐一个 300 元以内的鼠标
客服：返回鼠标 A
用户：再推荐一个
```

预期：新查询继续携带鼠标品类和 300 元上限。

### 场景八：省略问题谓词

```text
客服：返回鼠标 A、鼠标 B
用户：第二个支持蓝牙吗
客服：回答鼠标 B 的蓝牙能力
用户：第一个呢
```

预期：继承“是否支持蓝牙”，查询或回答鼠标 A；不能复用鼠标 B 的答案。

## 9. 已确认决策

1. 单候选返回后自动写入 `active_product_code`。
2. 用户明确切换商品品类后，删除上一品类的全部商品上下文；新查询失败也不恢复。
3. 用户重新提到旧品类但未指定商品时，先询问是否重新查询，并保存受控的
   `pending_query`；用户明确肯定后执行查询。
4. 同品类再次推荐继承有效筛选条件，直到用户明确修改或移除；筛选条件不跨品类继承。
5. 允许继承白名单内的问题谓词，但仅限当前候选批次，且只能继承问题、不能继承答案。

## 10. 实施顺序

1. 先根据本文编写状态契约测试和完整场景失败测试。
2. 实现 `ProductContext`、`ProductCandidateBatch`、受控问题谓词和待确认查询契约。
3. 实现品类切换、同品类替换、筛选继承和状态清理的确定性转移。
4. 实现 `pending_query` 的肯定、否定、打断和过期处理。
5. 实现当前批次内的序数解析和问题谓词继承。
6. 接入真实商品 Tool、Result 契约和 CommitCoordinator。
7. 跑商品专项回归、客服关键回归、Pyright 和完整测试。
